# Personalisation — the shopper-segment model

SmartBuy AI has one trained machine-learning model. It reads a user's
interaction history, predicts which of four **shopper segments** their
behaviour looks like, and the application attaches a discount or a perk to that
prediction.

Everything else in the product is deterministic scoring or LLM language. This
is the only component that learns.

---

## Read this first: what the accuracy figure means

The segment labels this model is trained against are **generated by
`backend/scripts/seed.py`**. The catalog and the interaction log are synthetic
(see [DATASET.md](DATASET.md)).

So the honest claim is:

> Given behavioural data that contains segment structure, this pipeline
> recovers the segment on users it has never seen, **96.8%** of the time,
> against a stratified-guess floor of **17.5%**.

That is a real result about the *pipeline* — it catches feature bugs, leakage,
and train/serve skew, which is exactly what it is there to do. It is **not**
evidence about how real shoppers behave, and the number must not be presented
as if it were. The same caveat is written into
`ml/personalization/model/training_report.json` and into the header of
`ml/personalization/train.py`.

## The four segments

Defined once, in [`backend/app/ml/segments.py`](../backend/app/ml/segments.py).

| Segment | Shown to user | Behaviour | Offer | Coupon |
|---|---|---|---|---|
| `deal_seeker` | Deal seeker | Browses and buys heavily discounted items; converts markedly more when the discount is deep | 10% off | `SMARTBUY10` |
| `window_shopper` | Still deciding | High browsing volume, very few purchases | 15% off | `FIRSTBUY15` |
| `brand_loyal` | Brand loyal | Activity concentrates on a small number of brands | 5% off + early access to those brands | `LOYAL5` |
| `premium_buyer` | Quality first | Buys high-rated, higher-priced items; converts without a discount | Free express delivery + extended returns | — |

The policy follows one rule: **discount where a discount changes the outcome,
and not where it only costs margin.** A `premium_buyer` gets service rather
than price, because discounting a segment that already converts is margin spent
on nothing.

### Why the policy is not inside the model

`segments.py` is separate from the classifier on purpose. The model answers
*"which segment does this behaviour look like"*. Deciding what to **do** about
that answer is commercial policy, and policy buried in a model artifact is
policy nobody can review or change without a retrain. Editing a discount here
requires no retraining at all.

## Features

27 per-user features, built by
[`backend/app/ml/features.py`](../backend/app/ml/features.py). The **same
function builds them at training time and at serving time** — there is no
second implementation to drift.

| Group | Features |
|---|---|
| Volume | `n_events` |
| Event mix | `rate_viewed`, `rate_clicked`, `rate_saved`, `rate_liked`, `rate_disliked`, `rate_purchased`, `rate_not_interested` |
| Funnel | `engagement_rate`, `conversion_rate`, `negative_rate` |
| Price | `mean_price`, `median_price`, `price_spread`, `purchase_mean_price` |
| Discount | `mean_discount`, `max_discount`, `purchase_mean_discount`, `discount_gap` |
| Quality | `mean_rating`, `mean_review_count`, `mean_delivery_days` |
| Breadth | `n_distinct_products`, `n_distinct_categories`, `n_distinct_brands` |
| Concentration | `brand_concentration`, `category_concentration` |

Users with no interaction history are **omitted from the feature set, not
zero-vectored**. A zero vector is a confident-looking input describing a person
we know nothing about, and the model would happily classify it.

## Training

```bash
python ml/personalization/train.py
```

- 250 labelled users with ≥ 10 events (`MIN_EVENTS`)
- 75/25 stratified train/test split, `random_state=42`
- Candidates: `RandomForestClassifier(n_estimators=300, min_samples_leaf=2, class_weight="balanced")` vs `StandardScaler → LogisticRegression`
- Chosen by 5-fold CV on `f1_macro`
- Baseline: `DummyClassifier(strategy="stratified")` — measured, not assumed, because "we got 82%" is unreadable without a floor

### Result (`ml/personalization/model/training_report.json`)

```

classes: brand_loyal 62 · deal_seeker 66 · premium_buyer 62 · window_shopper 60

  random_forest        cv f1_macro = 0.925 (+/- 0.018)
  logistic_regression  cv f1_macro = 0.914 (+/- 0.037)

chosen: random_forest
  holdout accuracy  0.968   (stratified guess 0.175)
  holdout macro F1  0.968
```

Confusion matrix (rows = true, cols = predicted):

|                | brand_loyal | deal_seeker | premium_buyer | window_shopper |
|----------------|---:|---:|---:|---:|
| brand_loyal    | 15 | 0  | 1  | 0  |
| deal_seeker    | 0  | 17 | 0  | 0  |
| premium_buyer  | 1  | 0  | 14 | 0  |
| window_shopper | 0  | 0  | 0  | 15 |

Two errors in 63 holdout users, both between `brand_loyal` and
`premium_buyer` — the two segments whose price and rating behaviour genuinely
overlap.

### What the model keys on

| Feature | Importance |
|---|---:|
| `mean_discount` | 0.202 |
| `n_events` | 0.143 |
| `n_distinct_products` | 0.117 |
| `mean_rating` | 0.093 |
| `brand_concentration` | 0.081 |
| `purchase_mean_discount` | 0.055 |
| `rate_purchased` | 0.049 |
| `conversion_rate` | 0.046 |

These are the behaviours the segment definitions describe, which is the result
you want: the model is not keying on some incidental artifact.

## Serving

[`backend/app/services/personalization.py`](../backend/app/services/personalization.py)
loads the artifact once per process and scores on demand.

**Three refusals are built in.** Each one exists because the alternative is a
confident wrong answer:

1. **Too little history** (`n_events < min_events`) → `insufficient_history`.
   Under the threshold the vector is mostly zeros; the model would still return
   a class.
2. **Low confidence** (`< MIN_CONFIDENCE = 0.55`) → `low_confidence`. Guessing
   someone's segment and discounting on the guess is how personalisation ends
   up feeling arbitrary.
3. **Feature mismatch** — if `feature_names` in the artifact does not match
   `FEATURE_NAMES` exactly, the model is refused. A model fed columns in a
   different order does not error, it returns confident nonsense. This is the
   entire reason the names are stored alongside the model.

A missing or unreadable model file is normal, not an error: a fresh clone must
boot before anyone has run `train.py`. It degrades to `model_unavailable`.

**The model never writes to the database.** It proposes an offer; persisting a
discount is a commercial action and stays behind the normal validated paths.

### API

```
GET /api/personalization      (scoped to the caller's session)
```

```json
{
  "segment": "deal_seeker",
  "label": "Deal seeker",
  "confidence": 0.888,
  "rationale": "Browses and buys heavily discounted items, and converts markedly more often when the discount is deep. A coupon moves this basket.",
  "discount_pct": 10,
  "coupon_code": "SMARTBUY10",
  "perk": null,
  "events_considered": 61,
  "status": "ok",
  "is_model_generated": true
}
```

`status` is `ok | insufficient_history | low_confidence | model_unavailable`.
Anything other than `ok` means **no offer was issued and the reason is stated
rather than hidden**.

There is deliberately **no route to read another user's segment**. An inferred
spending profile is exactly the kind of derived personal data that should not
be readable by id.

### UI

[`frontend/src/components/profile/PersonalizedOffer.tsx`](../frontend/src/components/profile/PersonalizedOffer.tsx),
on the profile page. It renders the segment label, the confidence, the
rationale, and the coupon — and when the status is not `ok` it says so in
plain words instead of rendering nothing, so a demo can never imply that
everyone receives a coupon.

## Reproducing from scratch

```bash
python backend/scripts/seed.py --interactions 15000
```

```bash
python ml/personalization/train.py
```

The seeder assigns each synthetic user a latent segment that actually drives
which products they interact with and how often they convert. An earlier
version stored a `price_bias` it never used and drew `interaction_type`
independently of the product — the resulting data had no learnable structure at
all, and the first two model framings sat at chance. That is worth stating:
the fix was to the data generator, not to the model.

## Honest limitations

- Trained on synthetic behaviour. See the caveat at the top.
- `UserPreference.segment` holds ground truth **for seeded users only**. It is
  empty for real users, because a real deployment has to predict the segment
  rather than be told it. It is never read as a substitute for a prediction.
- No online learning. The model is a file; it changes when someone runs
  `train.py`. There is no claim here of learning from live traffic.
- Four segments is a modelling choice, not a discovered structure. Nothing
  here clusters users to find out how many segments there really are.
